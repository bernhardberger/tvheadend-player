# UX inventory for 1.0

**Status:** Agent draft, 2026-10-11, from the code at `9dc19155` and the offline
captures rendered from it. First owner pass 2026-10-12: "not far off", but every
screen needs rework, polish or missing features beyond what the code shows; the
owner's direction is recorded as **Owner direction** blocks and in the
cross-cutting list. Where the draft and the owner disagree, the owner wins.
**Scope:** Every user-facing screen of the remote-first app: current state,
unfinished parts, visible nits, gaps, open trials and stale documentation. It
feeds the screen packages U3–U10 in `roadmap-1.0.md`. It is not a design and
authorizes no implementation.

Conventions: paths are relative to
`app/src/main/java/at/bernhardberger/tvhplayer/` unless they start with `app/`,
`docs/` or `artifacts/`. Captures are under `app/build/outputs/` (ignored,

## Cross-cutting findings

These recur on several screens and are better decided once than per screen.

1. **No context actions.** Long-press and Menu do nothing on Channels, Guide
   and Recordings. The only long-press in the app is in the player's channel
   drawer (`ui/player/ChannelDrawer.kt:279`). Every action sits behind OK and a
   details panel. Owner: agreed, a known gap.
2. **Details surfaces differ.** Channels has a passive, never focusable preview
   with a 2–3 line synopsis. The Guide uses a dialog panel. Live player info is
   a full-screen page with Details/Schedule tabs. Recording player info is a
   text side panel with only Close. All share `ProgrammeDetailsLayout`, but
   their actions, Back handling and reach differ. Owner: agreed.
3. **Loading, empty and error states are inconsistent.** There are three
   message vocabularies for the same connection states: startup
   (`main_startup_*`), Channels (`status_connection_failed_*`), and
   Guide/Recordings (`epg_*`, `recordings_*`).
   - Channels has a delayed spinner; Guide and Recordings show text only.
   - Recordings offers no Connection settings action, and shows "No recordings
     are available." for an unconfigured or credential-less state
     (`ui/screens/recordings/RecordingsContent.kt:792-829`).
   - The Guide says "Retry the server connection" while showing a
     Connection settings button (`ui/screens/EpgGridScreen.kt:2383-2387`,
     `ui/screens/guide/EpgGridContent.kt:671-691`).
   - Destination loading placeholders are still deferred (`docs/DESIGN.md:160-169`).

   Owner: the whole error delivery and recovery needs an overhaul, not
   per-string fixes.
4. **Remote keys.** With the accessibility service off, no foreground code
   handles GUIDE or TCL's TV key `4001`. The owner saw both reach the app and
   land on wrong screens, so TCL probably delivers them as other key codes;
   roadmap U14 step 1 records the real codes. No code anywhere handles the
   colour keys, `LAST_CHANNEL`, `TV_INPUT` or `SEARCH`, nor `MEDIA_RECORD`
   outside startup. LIST keys work only in the live player. Number keys work
   only in the live player.
5. **Back and the TV quality rule TV-DB** (Back from the top level returns to
   the launcher):
   - From Guide, Recordings or Settings it takes three Backs to leave.
   - On Channels, Back can reopen a still-running player once instead of
     leaving (`core/BackNavigationPolicy.kt:34-41`).
   - With autostart, the player is the root and the browse stack is cleared
     (`ui/AppRoot.kt:620`).
   - On onboarding, system Back probably leaves the app from the connection
     step, because there is no `BackHandler` (inferred, not observed).
   - Owner: entering a screen from the side rail is also a problem; focus lands
     in inconsistent places. Deliberately untouched until the screens are
     feature complete, then fixed together with Back.
6. **Product name casing.** Resolved: "Tvheadend Player" on screen is correct
   (owner; `docs/product-identity-plan.md:10-11`). Engineering docs that write
   "TVHeadend Player" in prose (for example the `AGENTS.md` title) are the
   ones out of line; the HTSP client name `TVHeadend Player / <version>` is
   specified separately and stays.
7. **Dead code and unused strings** from earlier layouts:
   - The Guide category filter is unreachable: `ui/AppRootDestinationContent.kt:105`
     passes no category and `onClearCategory = {}`.
   - Unused strings:
     - Guide: `epg_details_action_hint`, which is also wrong now; `epg_jump`;
       `epg_schedule`; `epg_time_duration`.
     - Recordings: `recordings_folder_recent_in`, `recordings_upcoming_active`,
       `recordings_completed`, `recordings_failed_cancelled`,
       `recordings_schedule_end_duration`.
     - Settings: `timeshift_setting_description`,
       `refresh_rate_matching_setting_description`,
       `auto_start_playback_description`.
   - The player chrome keeps "retained trial caller input" parameters
     (`ui/player/PlayerChrome.kt:98-108`, `ui/player/PlayerChromeControls.kt:95`).
8. **Raw technical text reaches viewers.** The player's unavailable box
   appends the recovery reason name, the player error code and the target
   result (`ui/player/VideoPlayerScreen.kt:1984-1998`; capture
   `unavailable-en-font1.0.png` shows `ERROR_CODE_IO_UNSPECIFIED`). Owner: not

9. **Capture coverage gaps.** There are no current captures of:

### Warm playback and browse backgrounds (draft, 2026-10-14)

Product principle (owner): playback stays available while browsing. Without
one rule, every screen would invent its own art/video handling, so the shell
decides and screens only ask.

- **Inputs:** what plays behind the browse screens (live, a recording, or
  nothing; the shell's warm-playback target), and later the settings below.
- **Output, decided once in the shell:** the background of a browse surface is
  the video, programme art, or the plain theme, plus the scrim strength (today
  one 0.84 black scrim, `DESIGN.md` §4).
- **Rules agreed so far:**
  - Video plays behind → the video is the background; surfaces draw no art.
    This holds for details pages (built 2026-10-14) and, probably, Home (owner:
    "probably no" art while video plays).
  - A recording playing behind behaves like live (owner, 2026-10-14).
  - Nothing plays → surfaces may use their art (details: top-right hero) or the
    theme background.
- **Later settings (U7):** switch warm playback off; possibly prefer art over
  the video on details pages. With warm playback off, leaving the player
  stops playback (owner leans "stop"): it frees the tuner, network and decoder;
  a muted stream would keep a tuner busy that recordings or other clients may
  need. The cost is a fresh tune when returning to the player.
- **Code today:** the shell passes one flag (`LocalWarmPlayback` in
  `ui/AppRoot.kt`, on the U15 polish branch); it grows into the richer output
  above only when the settings arrive.

## Splash, startup and app-wide feedback

**Today**
- The native splash is held for up to 1000 ms (`ui/MainActivity.kt:162`,
  `:184-187`, `:295`). The brand intro plays once per process
  (`StartupBrandTimeline.kt:11`).
- The in-app startup screen shows only for autostart or appliance launches
  (`ui/startup/MainStartupPresentation.kt:53-58`). Its stages are Preparing,
  Connecting, "Syncing channels and guide", "Preparing channels", then
  Starting or Resuming playback (`MainStartupPresentation.kt:60-102`).
- The whole sync is one SDK state, so the longest phase shows one unchanging
  line.
- Spinner and text appear after 400 ms
  (`ui/startup/MainStartupLoadingFeedback.kt:5-14`).
- Failures (unreachable, sign-in, denied, unsupported, timeout, sync, no
  channels) give Retry and/or Connection settings, depending on the SDK's
  recovery disposition. Automatic backoff shows a passive "Reconnecting" with
  no buttons and no time limit (`MainStartupPresentation.kt:99-100`).
- Notices: one non-focusable host at bottom centre over everything
  (`ui/notifications/AppNoticeHost.kt`), 4 s for information and 6 s for
  failures.
  - Kinds: 8 DVR changes, 7 DVR action failures, connection
    lost/restored/login rejected, cache clear, background playback.
  - "Connection lost" posts after a prior Ready and a 3 s debounce, and is
    gone after 6 s.
  - Connection, cache and background notices have no icon.
- Player recovery overlay: "Connection interrupted. Reconnecting
  automatically…" or "Playback stopped." with Retry/Close.

**Unfinished**
- Owner, 2026-10-11: the channel and guide sync on the splash lasts long and
  needs more granular information or stages so it never looks hung. This
  conflicts with the `DESIGN.md:126-139` rule. It pairs with E5 (startup work).
- No persistent connection status after the notice disappears (comparable apps).
- No "last updated" or offline indication for cached Guide or Recordings data.

**Owner direction (2026-10-12)**
- More stages, or better, more verbose stages with an X/Y count like Kodi.

**What the SDK can report today** (sdk-core 0.24.0 sources): nothing beyond
"synchronizing". `SessionState.Synchronizing` is a plain object, and the
repositories keep publishing the previous snapshot until HTSP's
`initialSyncCompleted`. The app enables async metadata with the EPG included
(`HtspProtocolGateway.kt:391`, horizon from `epgCoveragePolicy`).

**What the server sends** (Tvheadend `src/htsp_server.c`,
`htsp_method_async` and `htsp_epg_send_waiting`, checked 2026-10-12): all tags,
then all channels, then tag mappings, autorecs, timerecs and recordings, then
the guide channel by channel (each channel's programmes in start order up to
the window), then `initialSyncCompleted`. There are no totals, but every
channel is known before the first programme arrives, so "guide: channel 41 of
120" can be counted on the client. That is an SDK addition for the SDK owner.

**What Kodi does** (xbmc `pvr/PVRManager.cpp` and `pvr/epg/EpgContainer.cpp`,
checked 2026-10-12): the startup dialog uses fixed steps, not counts: "Loading
channels and groups" at 0 %, timers at 50 %, recordings at 75 %, and it is
dropped after 30 s. The X/Y is the separate "Loading programme guide" dialog,
which shows the channel name and "channel N of M" while Kodi walks its own
per-channel guide tables. So a count per channel matches what Kodi shows.

**Owner concern about loading the guide later** (2026-10-12): the app is close
to useless without a guide; Home, Channels, the Guide and the player would show
placeholders for seconds. If anything, now/next must come first. Two facts
bear on this:
- The persistent cache (`docs/persistent-cache-plan.md`, SDK cold-start
  publication) already shows the previous guide during a sync on warm starts.
  Placeholders would only appear on the first run, after "Clear cache" or
  after a long absence. Why the splash still waits so long on warm starts is an
  E5 question.
- HTSP can deliver now/next first. Every `channelAdd` carries `eventId` and
  `nextEventId`, and the guide window is adjustable: a first request with a
  short window (the server's minimum is 10 minutes) sends roughly now/next
  before `initialSyncCompleted`, and a second request that widens the window
  makes the server send the remaining programmes as updates. Reading the
  server code suggests this works; it is not tested, and it is an SDK design
  question.

**Owner direction (2026-10-12, second pass)**
- The splash shape follows the E5 outcome. If startup waits only for now/next
  and that is fast enough, today's splash can stay, with somewhat more detailed
  stages. If startup still waits for the guide, that is the long blocking wait
  and gets a progress count. If the guide loads in the background while the
  app is usable, the splash needs no granular sub-progress.
- SDK owner (2026-10-12): initial-sync progress (stage, guide channel N of M,
  approximate) comes in SDK 0.27. Now/next first is not small; the owner
  skipped it. The SDK owner times the sync with a 24 h versus 2 h window on
  the real server as a data point.
- Without autostart the app already opens on cached data. With autostart the
  splash waits for the whole sync even on a warm start
  (`core/MainStartupPresentation.kt`), which is the startup case to fix (E5).

- Owner (2026-10-16): with autoplay off the app is "borderline unusable" until
  the HTSP connection, channels and recordings are there, so the existing
  animated splash, its stage messages and its error screen should also run on
  a cold start without autoplay, then enter the browse screens instead of the
  player. Decided the same day: an unreachable server offers only Try again
  and Edit connection (no "continue with saved channels").
- Revised by the owner the same day after the G10 cold-start runs: the splash
  stays until the cached channels and recordings are drawn, or without a cache
  until the initial sync finishes, with today's stage messages. No counts (the
  app only gets channel and guide counts when the sync finishes) and no guide
  wait or Skip action (on a fresh start channels and guide arrive together, so
  there is nothing earlier to enter). This replaces the earlier counts and Skip
  decision; the sync-progress request to the SDK is not needed for it.
- Colours (owner 2026-10-16): the error colour stays the theme's light error
  tone (`#FFB4AB`) for text and icons, with no filled `#93000A` containers;
  recording red (`TvRecordingColor`, `#FF5449`) gets slightly stronger.

**Questions**
1. After long backoff, should startup offer Retry and Settings instead of
   waiting indefinitely?
2. Should "Connection lost" stay visible until it is restored?

**Recommendation (agent, for the U5 brief)**

  that covers TV-VS without a global search. Engage SDK (TV-EC, TV-ER, tier 1)

**Genre (owner, 2026-10-12, third pass)**

- Grid cells carry no genre hint at all: every cell has the same colour. The
  genre text appears only in details and the player tray.
- Owner: a filter maybe, scoped to predefined values such as genre; it needs
  its own decisions and slice. Genre presentation in the grid needs a UX
  decision, at the latest in the Guide rewrite (U5).

**Past programmes (owner, 2026-10-12, third pass)**
- Wanted if the cost is proportionate: seeing what was missed, and finding the
  information or recording for something that just ran.
- Tvheadend cannot supply them: it deletes each programme from its guide as
  soon as it ends (`src/epg.c`, `_epg_channel_timer_callback`), so no HTSP
  request returns past programmes.
- The SDK keeps them itself, in memory only: programmes the server deletes
  while the app is connected go into a history pruned at 6 h
  (`sdk-core/.../metadata/EpgReducer.kt`, `pruneHistory`). The persistent
  cache does not store that history, so a cold start has none.
- The candidate fix is an SDK change: persist the history with the cache, and
  on restore keep cached programmes that have ended (not checked whether the
  restore drops them today).
  Past programmes would then be there whenever the app saw them before they
  ended, which for a 7-day guide horizon is nearly always. Cost is for the SDK
  owner to estimate; recorded programmes are already reachable through their
  recordings.

- Decided: genre filter and genre presentation wait for the Guide rewrite
  (U5) and are decided there.
- SDK owner estimate (2026-10-12): medium, about 2–4 days with tests, no public
  API change at a fixed 6 h horizon (`EpgSnapshot.historicalEvents` exists).
  Today a restore keeps ended programmes only as ordinary stale events until
  the sync replaces them, and every reconnect also clears the history. It can
  show what was scheduled, not prove what aired. Recommended once the Guide
  commits to a history UI; not needed for 1.0.
